Scope: `docs/V1_SCOPE_AND_PHASES.md` P5. Builder's own checks: `backend/tests/test_face_layer.py` (11 tests) and `tests/test_tokens.py`.

## What changed since P4 (update your fixtures)
- `stub-v0` is rejected at `POST /students/me/enroll` -> 422 `BAD_MODEL`. Use model id **`faceapi-128-v1`** with a 128-float vector in fixtures. `GET /students/me/enrollment` now also returns `model`.
- With `GK_FACE_MODE=required` (default) a student whose template model is not `faceapi-128-v1` gets **409 `REENROLL_REQUIRED`** on `/challenge` and `/checkin`. Run the P1-P4 regression with `GK_FACE_MODE=off` (restores QR-only: VERIFIED, 0.5, `QR_ONLY`), or update fixtures.
- Challenge `expires_ms` is now about +60 s (was 15 s), because the face step runs before the QR scan. Colour set: red, green, blue, yellow, magenta, cyan (no white).
- `checkins` has a new `evidence` column: delete `gatekeeper.db` and re-seed.
- `POST /sessions/{id}/checkin` body adds optional `face: {vector: [128 floats], model}` and `liveness: {baseline: [r,g,b], samples: [[r,g,b] x4]}` (0-255). Response unchanged: `{checkin_id, status, score, flags, latency_ms}`.

## Scoring table (server, `app/trust.py`)
score = 0.5 (QR passed) + 0.3 (face distance <= 0.55) + 0.2 (liveness passed). VERIFIED needs score >= 0.8 and no review flag. Review flags: `FACE_MISMATCH`, `FACE_COLLISION`, `LIVENESS_FAIL`, `FACE_MISSING`, `LIVENESS_MISSING`. REJECTED is never produced here. Audio is P6.

## API cases
1. Right face + good liveness -> 200 VERIFIED, score 1.0, flags [].
2. Wrong person (vector distance > 0.55 from own template) -> REVIEW + `FACE_MISMATCH`, score 0.7; if it is within 0.55 of another rostered student's template, that student's id is in `evidence.looks_like` (DB check).
3. **Mule simulation**: the same vector under 3 student IDs in one session -> the 2nd and 3rd get `FACE_COLLISION`, and the 1st is pulled to REVIEW with `FACE_COLLISION` too (check `/checkin/me` of the first). Vectors 0.46+ apart must not collide. Try 20 students with random vectors: zero collisions.
4. Liveness: flat samples (no colour reaction) -> `LIVENESS_FAIL`; brighter-but-not-coloured samples -> fail; samples for the wrong colours (e.g. replay of another challenge's data) -> fail; 3 of 4 correct steps -> pass; missing `liveness` or `challenge_id` -> `LIVENESS_MISSING`.
5. Challenge handling: used once (second check-in attempt with the same challenge by another student -> `LIVENESS_FAIL`, never a 5xx); other student's/other session's/expired/unknown challenge -> `LIVENESS_FAIL`.
6. Face-optional path: no `face` at all -> 200 REVIEW with `FACE_MISSING` + `LIVENESS_MISSING` (never 4xx/REJECTED). `face.model` other than `faceapi-128-v1` -> treated as missing.
7. Validation: vector length != 128, non-finite numbers (`Infinity`), rgb outside 0-255 -> 422.
8. **Privacy**: inspect every `/checkin` request body in the E2E run: only numbers, no image bytes/blobs/data URLs; request size well under 4 KB.
9. Idempotency still holds with face fields (20 simultaneous identical submissions -> one row, same id). Collision marking under concurrency: two colliding students submitting at the same instant may both miss each other (known, documented); if you see it, record the rate.
10. Enroll: `stub-v0` -> 422 `BAD_MODEL`; a `stub-v0` template student -> 409 `REENROLL_REQUIRED` on challenge/checkin; after DELETE `/students/me/face-data` and re-enroll with the new model they pass.
11. Load: repeat P4 case 9 (240 students) with face payloads; report p50/p95/p99. Server-side work is 240 distance computations per mismatch lookup and a per-session collision scan; target p99 <= 400 ms at 15 s spread.

## UI cases (student-pwa, fake camera with a video of a face where possible)
12. Enrollment selfie with no face in frame -> "No face found in the photo…" and nothing is uploaded. With a face -> uploads, vector is 128 numbers.
13. Re-enroll prompt: a confirmed student whose template is not `faceapi-128-v1` sees the retake screen with the upgrade notice; the old template is deleted only when the new photo contains a face.
14. Check-in order: tapping Check in -> front camera + neutral grey, then 4 colour flashes (about 450 ms each, never faster than 2/s), then the rear camera for the QR. Total time from tap to QR camera <= 4 s; QR to result still <= 1.5 s. Screen must be full brightness-looking colours; the small face circle stays visible.
15. No face visible -> after about 4 s "Can't see your face…" with **Continue without face check**; choosing it ends in REVIEW + `FACE_MISSING`. Front camera denied -> goes straight to the QR step, result REVIEW.
16. Model load: the 3 weight files are requested from the same origin (`/models/*`), once, from the Home screen before the check-in is opened; second visit served from cache. Report first-load time on 4G and mid-range Android/iPhone.
17. Bundle: main JS 159.7 KB (<= 200 KB); `face-api` lazy chunk 1.33 MB (340 KB gz); report real transfer sizes.
18. **Real devices (needed for the exit criterion; builder could not run these):** wrong-person phone and 2-phones-one-face are flagged REVIEW; and a calibration run, at least 20 live check-ins by 5+ different people in each of: bright room, dim room, projector-lit room, with and without glasses. Record `evidence.face_dist` and `evidence.liveness_cos` per check-in (they are stored) and report false-REVIEW rate for honest students plus how often a photo of a face shown to the phone passes liveness. These numbers decide whether the single thresholds (0.55, 0.3, 3-of-4) hold.
