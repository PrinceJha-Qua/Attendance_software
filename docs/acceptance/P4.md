# Phase 4 acceptance: Student check-in core (QR only)
Scope: `docs/V1_SCOPE_AND_PHASES.md` P4. Dev password `gatekeeper-dev`. Backend `uv run uvicorn app.main:app`; apps `npm run dev` in `student-pwa` (5173) and `prof-console` (5174). To make seeded students check-in-eligible, enroll them via the API/UI and confirm as the professor (or insert `confirmed` FaceTemplate rows in the test fixture).

## Real endpoints in P4 (4)
`GET /sessions/active` (student), `POST /sessions/{id}/challenge`, `POST /sessions/{id}/checkin`, `GET /sessions/{id}/checkin/me`. `GET /sessions/{id}` now returns the real `checked_in_count`.

## API cases
**Active list and challenge**
1. `/sessions/active`: only `live`/`paused` sessions of courses the student is rostered in; `checked_in` true once they have checked in; empty before start and after... (close arrives in P7). A student not on the roster sees nothing. `/sessions/active` must never be captured by `/sessions/{session_id}` (student gets 200, not 403).
2. `/challenge`: live session + confirmed enrollment -> `{challenge_id, expires_ms (about +15 s), colour_seq (4 colours)}`; not on roster -> 404 `SESSION_NOT_FOUND`; session not live -> 404 `SESSION_NOT_ACTIVE`; enrollment not confirmed (none/pending/rejected) -> 409 `NOT_ENROLLED`. Each call stores a new row; sequences are random.

**Check-in gates** (body `{qr, challenge_id?, scanned_at_client_ms?, device?}`)
3. Valid current QR -> 200 `{checkin_id, status: "VERIFIED", score: 0.5, flags: ["QR_ONLY"], latency_ms}`. Also valid with the previous window (grace 1). Row appears in `checkins`; professor's `checked_in_count` increments.
4. Rejections: garbage string or wrong prefix, forged token, or a session id different from the path -> 403 `TOKEN_INVALID`; valid-but-old window (older than grace) and future window -> 410 `TOKEN_EXPIRED`; QR from session B posted to session A -> 403; session paused/created/closed -> 404 `SESSION_NOT_ACTIVE`; student not on roster -> 404; enrollment not confirmed -> 409 `NOT_ENROLLED`; professor token -> 403; no token -> 401; `qr` empty or >256 chars -> 422.
5. Idempotency: a second POST (same or newer QR) returns 200 with the **same** `checkin_id` and no new row, including 20 simultaneous submissions from one student (exactly one row; never a 500; `IN_PROGRESS` 409 is acceptable only transiently, a retry must then return the same result).
6. `/checkin/me`: `{status:"PENDING"}` before check-in, the same result body after; other students' check-ins are never visible.
7. The per-student nonce does not block other students: N students posting the same QR in the same window all succeed (this is the bug the spec had).
8. Replay: a captured valid request replayed by a different student account with the old QR after the grace window -> 410; replayed by the same student -> same stored result.

**Load / timing** (SQLite WAL in dev; repeat on Postgres+Redis once available)
9. 240 students (create accounts via roster import, confirm enrollment in bulk) check in within 15 s, then within 5 s: 0 5xx, 0 lost check-ins, `checked_in_count` = 240; report p50/p95/p99 and the `latency_ms` field distribution. Targets (BUILD_PLAN B-PERF-01): p99 <= 400 ms at 15 s spread, <= 800 ms at 5 s. Also run 240 within a single QR window ("thundering herd").
10. Nonce store: with `GK_REDIS_URL` set to a real Redis, claim latency average < 2 ms; keys expire after 5 s; with Redis down the endpoint must fail closed with a clean 5xx error body (report current behaviour; fixing is a P9 item).

## UI cases (student-pwa; Chromium + WebKit; camera fakeable with `--use-file-for-fake-video-capture=<mp4 of a QR>`)
11. After enrollment is confirmed the student sees "Today"; with a live session a **Check in** button appears within 5 s of the professor pressing Start; paused shows "Class is paused"; after check-in shows "Checked in ✓".
12. Scan screen asks for the rear camera, shows live video, decodes a QR played from a video (rotating QR from `/project/:id` captured as video, or a recorded loop) and lands on "You're checked in ✓" without any extra tap. Measure and report time from QR fully visible to result screen on a mid-range Android and an iPhone (target P50 <= 1.5 s here, QR only).
13. Wrong-class QR -> hint "belongs to a different class" and scanning continues; stale QR -> hint "That code just changed…" and scanning continues (no infinite resubmission of the same stale payload: the same text is not resent within 2.5 s); not-enrolled / not-active -> blocking message with Back.
14. Camera permission denied -> "Camera needed" screen; Cancel/Back returns Home and releases the camera (indicator off).
15. Decoder selection: native `BarcodeDetector` is used where available (Chrome Android), zxing-wasm on Safari/iOS; wasm file is served from the same origin (no request to a CDN: check the network log) and is requested on the Home screen before the Scan screen is opened.
16. Bundle budget: first-load JS <= 200 KB (currently ~156 KB main + 37 KB lazy zxing chunk; wasm 947 KB loaded lazily); report actual.
17. Two-device end to end: professor projection on a laptop/projector, student phone at 2 m, 5 m, and the farthest reachable distance: success rate over 20 attempts each and typical time-to-check-in; record phone model, step_ms, QR size slider setting. (First real data for the QR legibility question; feeds the room trials.)

## Known placeholders (do not fail these)
No face or audio verification, no liveness (challenge is issued but not consumed), trust score is the constant 0.5 with flag `QR_ONLY`, no rate limiting (P9), no `close` or attendance records (P7), no torch/zoom controls.
