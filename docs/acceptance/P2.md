# Phase 2 acceptance: Courses, roster, enrollment
Scope: `docs/V1_SCOPE_AND_PHASES.md` P2. Backend from `backend/` (`uv run uvicorn app.main:app`); apps: `student-pwa` and `prof-console` (`npm install && npm run dev`, Vite proxies `/api` to :8000; prof console on :5174). Dev password `gatekeeper-dev`.

## Real endpoints in P2 (13, all stubs removed)
`GET/POST /courses`, `PATCH /courses/{id}`, `POST /courses/{id}/roster/import`, `GET /courses/{id}/roster`, `GET /courses/{id}/enrollments/pending`, `POST /courses/{id}/enrollments/{student_id}/confirm|reject`, `GET /students/{id}/photo?exp=&sig=`, `POST /students/me/consent`, `POST /students/me/enroll`, `GET /students/me/enrollment`, `DELETE /students/me/face-data`.

## API cases
**Courses**
1. Create (201) with defaults required_pct=75, excused_counts=true. `GET /courses` lists only the caller's courses (second professor sees none of them). PATCH validates: required_pct outside 1..100 -> 422; planned_total_sessions <1 -> 422; setting planned_total_sessions to null clears it.
2. A professor touching another professor's course on any `/courses/{id}/...` route -> 404 `COURSE_NOT_FOUND`. Student token on any prof route -> 403.

**Roster CSV** (`file` multipart; header must contain roll_no,name,email, case-insensitive, UTF-8 with/without BOM)
3. Valid rows: existing students are added; unknown students get an account with a random password returned once in `created_accounts`; the new account can log in with it.
4. Errors are per row and do not abort other rows: missing/invalid field (`MISSING_OR_INVALID_FIELD`), duplicate email or roll within the file (`DUPLICATE_IN_FILE`), email and roll belonging to different users (`EMAIL_ROLL_CONFLICT`), identifier belonging to a professor (`NOT_A_STUDENT_ACCOUNT`).
5. Re-importing the same file is idempotent (`already_on_roster` counts, no new accounts). Missing columns -> 422 `CSV_MISSING_COLUMNS`; non-UTF-8 -> 422 `BAD_CSV`; >1000 rows -> 413; >1 MB -> 413. Time a 300-row import with all-new students (argon2 per row); report seconds.

**Enrollment (student)**
6. Enroll before consent -> 409 `CONSENT_REQUIRED`. After consent: valid JPEG/PNG <=500 KB + 128 finite floats + model -> 202 status pending. Bad vector (wrong length, NaN/Infinity, strings, bool) -> 422 `BAD_FACE_VECTOR`. Non-image bytes (even with .jpg name) -> 422 `BAD_PHOTO`. >500 KB -> 413 `PHOTO_TOO_LARGE`.
7. Enroll again while pending or confirmed -> 409 `ALREADY_ENROLLED`. After rejection, enrolling again replaces the template (status back to pending). After DELETE face-data, enrolling again works.
8. `GET /students/me/enrollment` -> `{consent_given, status: none|pending|confirmed|rejected, confirmed_at}`. DELETE face-data is 204 and idempotent; template row and photo are gone; audit row written.
9. Stored photo bytes in the DB are ciphertext (do not start with FF D8 FF / PNG magic) and decrypt back to the original.

**Confirm / reject / photos**
10. Pending list contains only students on that course's roster with status pending, each with a `photo_url`. Confirm/reject sets status, `confirmed_by`, `confirmed_at`; a second decision -> 409 `NOT_PENDING`; a student not on that roster -> 404.
11. Photo URL: works with the signing professor's token (200, image bytes, `Cache-Control: no-store`); no token -> 401; another professor's token -> 403 (signature is bound to the professor); tampered sig or expired exp (set `PHOTO_URL_TTL_S=1`) -> 403; student not on any of the professor's courses -> 404. Each successful view writes an `audit_log` row `photo.viewed`.
12. Roster endpoint shows `enrollment` per student; `confirmed_count` on `/courses` matches.

**Security**
13. IDOR: student A cannot read/delete student B's data through any route; professors cannot fetch photos of students outside their courses. SQL injection strings in CSV cells and course names are stored as plain text. `GK_ENV=prod` without `GK_PHOTO_KEY` refuses to start.

## UI cases (manual or Playwright, Chromium + WebKit; camera can be faked with `--use-fake-device-for-media-stream`)
**Student PWA** (`student-pwa`)
14. Login (roll no or email), wrong password message, professor account is refused. New student flow: consent screen -> selfie screen -> "waiting" screen. Waiting screen updates to "You are enrolled" within ~5 s after the professor confirms. Rejected -> retake prompt.
15. Camera denied -> file-picker fallback appears. Retake works. Large phone photos are downscaled (<=640 px) and upload succeeds. Delete-my-face-data returns the student to the selfie screen.
16. Layout at 360x640 and 390x844: no horizontal scroll, buttons >= 44 px tall. Production bundle <= 200 KB JS (currently ~150 KB; report actual).

**Professor console** (`prof-console`)
17. Login (student account refused). Create course, edit required % and planned sessions, upload CSV, see result message with error row numbers, download the one-time logins CSV. Pending cards show the photo (fetched with auth) and Confirm/Reject update the list and counts.
