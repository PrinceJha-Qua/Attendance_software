# Phase 6 acceptance: Audio layer (ultrasonic beacon, soft signal)
Scope: `docs/V1_SCOPE_AND_PHASES.md` P6 and `reports/Ultrasonic attendance audio reliability.md`. Builder's own checks: `bench/audio_sim.ts` (results in `docs/audio_sim_results.txt`: synthetic, all configurations decode 100/100 at 32-96 kHz, 0 false frames in 10 min of noise+tone) and 10 new tests in `backend/tests/test_face_layer.py`.

## What changed
- New real endpoints: `GET /sessions/{id}/audio-plan` (owner professor or rostered student; others 404, no token 401), `POST /trial/audio-log` (student; 204 always; stored only when `GK_TRIAL_MODE=1`). Both removed from stubs.
- `GET /sessions/{id}/tokens` items gain `audio_code` (int 0-65535) **only** when the session's `audio_mode` is `burst`.
- `POST /sessions/{id}/checkin` body gains optional `audio: {status: heard|none_heard|denied|unsupported, window_low8 (0-255), code (0-65535), snr_db}`. Numbers only.
- Scoring (sessions with `audio_mode=burst` only; others unchanged from P5): heard + correct window within 8 s -> no change; not heard/denied/unsupported/absent -> flag `AUDIO_UNAVAILABLE`, score -0.1 (a clean check-in is 0.9, still VERIFIED, never rejected); CRC-valid code that matches no recent window -> `AUDIO_MISMATCH`, -0.1 and REVIEW. `checkins.audio` stores the report; `evidence.audio` the verdict.
- Professor: "ultrasound beacon" checkbox when creating a session (default on); on the projection page an **Enable ultrasound beacon** button (a click is required by browsers), then a volume slider in the hover bar and a "beacon on" badge.
- Student: when the session has a beacon, the mic prompt appears at check-in start; listening runs through the face and QR steps.

## API cases
1. Tokens: burst session -> each token has `audio_code` equal to HMAC-derived value (see `tokens.audio_code`); off session -> field absent. Code differs from the QR `tok`.
2. Verdict table: correct current/previous-window code -> VERIFIED, flags [] ; `none_heard`, `denied`, `unsupported`, field absent -> `AUDIO_UNAVAILABLE`, score 0.9, never 4xx; valid code from ~60 s ago (replay) -> `AUDIO_MISMATCH`, REVIEW; random code -> `AUDIO_MISMATCH`; `window_low8` that matches a current window but a code from another session's secret -> `AUDIO_MISMATCH`.
3. Interaction: audio unavailable + face mismatch -> REVIEW, score 0.6; audio ok does not rescue a face mismatch.
4. Validation: code > 65535, window_low8 > 255, unknown status -> 422. Session with audio off ignores the field entirely (flags/score as P5).
5. `audio-plan`: returns mode, step_ms, band_hz [17500,19000], sample_rate, max_age_ms, trial_mode; other professor's session -> 404; unrostered student -> 404.
6. `audio-log`: non-trial -> 204 and zero rows; trial mode -> one row; body >4 KB of data -> 413 (trial mode); no image/sound bytes accepted anywhere.
7. Regression: full P1-P5 suites still green (the two audio stubs are gone from the stub list).

## Real-room trials (builder cannot run these; they are the exit criterion "decodes at >= 3 m on 2 devices, phone with no audio still checks in")
14. Two devices, one room: professor laptop (speakers) + phone at 1, 3, 6, 10 m: decode success over 30 bursts per distance, per phone model, at volume slider 25 and 50. Record `stats.maxNorm` (best correlation) for failures: it tells whether the burst was weak or absent.
15. Laptop speaker, projector speaker, 120-seat room speakers, 240-seat PA, TV speakers: does each reproduce 17.5-19 kHz at all (use `spikes/audio_emitter.html` + `audio_listener.html` first; the report predicts many TV/projector speakers roll off here). Record per room which devices hear it. This decides the audio tier per room type; the system already degrades to QR + face when it fails.
16. Safety/annoyance: a few people (including young adults) at 1 m for 5 minutes: audible? discomfort? Pets/other occupants? If audible at slider 25, lower the default.
17. Phone with no usable audio path (iOS with mic permission denied, old Android): check-in succeeds as VERIFIED 0.9 with `AUDIO_UNAVAILABLE` (never blocked).
